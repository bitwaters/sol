# 全量代码审查与修复记录（2026-09-13）

本轮覆盖 `src/` 全部生产模块、数据库模型与迁移、配置、`scripts/` 辅助脚本，以及相关测试和开发规范。按风险复查并直接修复，下列条目均已落地；也复核了上一轮尚未提交的周期绑定修复。定位指向当前工作区修复后的代码。

## 问题、推荐方案与处理结果

### 1. [P1] 重建可能把历史信号绑定到错误周期，检查点时间也可能替代真实建仓时间

定位：[src/signal/rebuild.ts:50](../src/signal/rebuild.ts#L50)。迟到成交拆分或合并周期后，原信号的退出判断与成本窗口可能漂移。

**推荐解决方案（已实施）**：保存成员加入时间、成交锚点和检查点周期元数据；重放时按成交恢复每个信号的周期，旧数据按可恢复证据兼容。

### 2. [P1] 采集与回补存在状态分离和同秒乱序

定位：[src/signal/ingest.ts:9](../src/signal/ingest.ts#L9)。回补回调失败或同秒成交分批到达时，成交、水位与持仓可能不一致。

**推荐解决方案（已实施）**：统一在 ingestBatch 事务内应用成交、重建和更新水位；按时间与事件 ID 排序，同秒迟到也重放；回补防重入并核对最新 cursor。

### 3. [P1] 缺口完整性依赖候选是否及时评估

定位：[src/store/repo/health.ts:31](../src/store/repo/health.ts#L31)。无候选评估的缺口超时后，持仓可能仍被视为成本完整；普通重放还可能提前清标记。

**推荐解决方案（已实施）**：发现缺口立即持久化影响钱包与缺口末端并撤销资格；门禁超时不等于恢复，重建需缺口后的可靠检查点。

### 4. [P1] 发送前有效票数、展示成员和追高均价可能来自不同成员集合

定位：[src/signal/candidate.ts:354](../src/signal/candidate.ts#L354)。钱包在异步富化期间失去资格时，消息分项和成本均价可能仍含已剔除成员。

**推荐解决方案（已实施）**：富化后重算最终窗口、钱包与代币条件；首次发送前原子刷新成员绑定和展示快照。

### 5. [P1] 异步候选评估可能用过期窗口或重复创建信号

定位：[src/signal/candidate.ts:522](../src/signal/candidate.ts#L522)。并发调用或富化跨过窗口、候选有效期时，可能产生重复任务或错误升级。

**推荐解决方案（已实施）**：同库同 token 合并并发评估；全部异步富化完成后重新读取时间、生命周期与窗口，再同步决定状态。

### 6. [P1] 已推送保留率剔除清仓成员，或错误引用重新买入周期

定位：[src/signal/members.ts:5](../src/signal/members.ts#L5)。清仓后分母缩小会使保留率反而升高，误导退出判断。

**推荐解决方案（已实施）**：使用固定绑定周期；清仓成员仍计入买入量分母，剩余量为零。

### 7. [P1] 429 处理可能绕过全局预算，延长封禁后仍提前继续

定位：[src/ingest/limiter.ts:113](../src/ingest/limiter.ts#L113)。非 JSON/业务限频响应或封禁延长时，可能重复触发 API 限频。

**推荐解决方案（已实施）**：统一交给 gateway 处理 429；默认关闭客户端自行重试，等待最新封禁截止；增加请求超时和权重校验。

### 8. [P1] 损坏归档仅按行数校验后仍可能清理数据库

定位：[src/ingest/archive.ts:47](../src/ingest/archive.ts#L47)。已有归档出现坏 JSON 或缺少成交字段时，继续合并清理会留下不可恢复的数据。

**推荐解决方案（已实施）**：读取旧归档与写后验证均检查成交结构；任何旧归档损坏则跳过该日，保留原文件和数据库。

### 9. [P2] 部分配置被接受但未参与业务判断

定位：[src/config.ts:20](../src/config.ts#L20)。自定义钱包上限、净流入上限、观察次数、聚类开关等不能产生预期效果。

**推荐解决方案（已实施）**：落实支持的参数；未支持的模式启动即报错；范围 null 不设边界，校验静默时刻与正数参数。

### 10. [P2] 动作过滤和追高计算口径不一致

定位：[src/signal/window.ts:88](../src/signal/window.ts#L88)。仅启用加仓或建仓时，按钱包整体动作过滤会错误计票或保留不合格买入成本。

**推荐解决方案（已实施）**：逐成交识别当前周期首笔建仓与后续加仓，并让均价只使用同一批合格成交。

### 11. [P2] 坏数字或坏行污染整批计算

定位：[src/ingest/normalize.ts:105](../src/ingest/normalize.ts#L105)。NaN、Infinity、负数或 null 行可能使 Decimal/富化失败，或错误获得成本资格。

**推荐解决方案（已实施）**：校验有限数字和时间；坏字段保留原始记录但不给计算资格，跳过结构坏行，缺买入金额标记周期 incomplete。

### 12. [P2] 钱包画像长期不刷新，部分缺失值状态与文档不符

定位：[src/signal/candidate.ts:628](../src/signal/candidate.ts#L628)。旧标签持续影响资格；社交缺失或权限尚未放弃可能被当作硬过滤并进入禁验期。

**推荐解决方案（已实施）**：过期画像按需刷新；按缺失值决策表暂缓权限/社交未满足的候选；无边界的范围不强制缺失字段。

### 13. [P2] 消息显示固定阈值及过期分项

定位：[src/telegram/format.ts:175](../src/telegram/format.ts#L175)。自定义窗口、强共识或追高阈值后，显示仍沿用默认值；弱化时成员分项未同步。

**推荐解决方案（已实施）**：渲染传入实际配置；使用独立 display_wallets 保存当前有效展示，并修正负净流入符号和 HTML 转义。

### 14. [P2] 暂停或生命周期变化发生在发送复核期间

定位：[src/telegram/pusher.ts:405](../src/telegram/pusher.ts#L405)。已领取任务可能在管理员暂停或候选终结后继续发送。

**推荐解决方案（已实施）**：复核返回后检查最新候选状态；调用 Telegram 前再次检查暂停/静音。

### 15. [P2] 退出任务排队后清仓条件可能已被重建纠正

定位：[src/telegram/pusher.ts:545](../src/telegram/pusher.ts#L545)。过期或已撤销的退出条件仍可触发错误提醒，取消后的去重键还可能阻止后续有效提醒。

**推荐解决方案（已实施）**：两类提醒发送前共用最新清仓判定并检查配置/期限；取消任务允许重新排队，纠正终止标志；实现 token 年龄 24 小时终止。

### 16. [P2] 回测请求与信号送达的基准切换存在竞争

定位：[src/backtest/evaluate.ts:181](../src/backtest/evaluate.ts#L181)。旧基准结果或缺行情次数可能污染已发送的新基准。

**推荐解决方案（已实施）**：发送成功清空旧结果和缺行情计数并保存 send_snapshot；异步请求后与写入时核对基准，拒绝旧评估。

### 17. [P2] 回测队列可能漏选更早到期的样本

定位：[src/backtest/evaluate.ts:115](../src/backtest/evaluate.ts#L115)。只在首批候选内排序会使其他样本长期得不到评估，网络错误还会耗尽缺行情额度。

**推荐解决方案（已实施）**：扫描到期候选后按最早缺失期限排序，防重入；过滤无效基准与蜡烛，网络失败不计为缺行情终止。

### 18. [P2] 回测分组会随编辑漂移，警告分组可能重叠

定位：[src/backtest/report.ts:45](../src/backtest/report.ts#L45)。票数、警告、来源和年龄按可变字段统计，影响策略比较。

**推荐解决方案（已实施）**：优先使用发送快照，兼容触发快照和数字字符串；警告与无警告互斥，补充来源组合分组；对照净流入与窗口口径一致。

### 19. [P2] 长期运行的统计报告可能超过消息长度

定位：[src/backtest/report.ts:195](../src/backtest/report.ts#L195)。拦截原因分组累积后，日报或 /stats 可能无法发送。

**推荐解决方案（已实施）**：按换行优先分段，保守限制每段长度并保护 Unicode 代理对；日报和命令共用分段。

### 20. [P2] 无成交阶段缺少运行告警，失败的每日维护未重试

定位：[src/ops/alerts.ts:21](../src/ops/alerts.ts#L21)。启动后源失联或推送耗尽重试可能无人知晓，备份/日报失败后当日不再尝试。

**推荐解决方案（已实施）**：根据启动时间和启用源监控心跳，报告耗尽任务；成功后标记备份日期，日报失败恢复重试；将 HTTP/HTTPS 代理接入运行入口。

### 21. [P2] 同票数成员替换未触发编辑，成员版本与消息修订混用

定位：[src/signal/candidate.ts:216](../src/signal/candidate.ts#L216)。有效成员替换但票数、保留率和价格相同时，原变化检测可能漏掉升级；价格修订还会被当作成员版本，影响成员追溯。

**推荐解决方案（已实施）**：把成员标识和展示分项纳入变化检测；被节流时保留已排队版本的完整显示数据，待节流结束再更新。只有新增固定成员时递增 `escalated_count`，新成员的 `joined_version` 使用该版本；其他可见变化只递增 `message_revision`，并兼容旧版本计数。

### 22. [P2] 声明的最低 Node.js 版本低于已安装依赖要求

定位：[package.json:8](../package.json#L8)。项目声明 Node.js ≥20，但当前依赖 `undici` 要求 ≥22.19.0、`better-sqlite3` 要求 ≥22，按原部署文档选择 Node.js 20 会遇到不受支持的安装/运行环境。

**推荐解决方案（已实施）**：将项目及锁文件根包的 engines 统一为 Node.js ≥22.19.0，同步开发环境说明与任务清单。
